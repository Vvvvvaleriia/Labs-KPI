# Специфікація

## 1. Опис задачі

Розробити концептуальну ER-модель для системи резервування столиків у ресторані, яка дозволяє користувачам переглядати доступні столики, обирати дату, час та кількість гостей, створювати та скасовувати резервування, а також залишати відгуки.

Модель повинна описувати користувачів, столики, типи столиків, резервування та відгуки, їх атрибути, ключі, зв'язки та основні обмеження.

## 2. Сутності та атрибути

### `User`

Сутність `User` представляє користувача системи.

Атрибути:

- `id` — унікальний ідентифікатор користувача, первинний ключ.
- `name` — ім'я користувача.
- `email` — електронна адреса користувача.
- `phone` — номер телефону користувача.
- `password_hash` — хеш пароля користувача.

### `Table`

Сутність `Table` представляє столик у ресторані.

Атрибути:

- `id` — унікальний ідентифікатор столика, первинний ключ.
- `table_number` — номер столика.
- `seats` — кількість місць.
- `table_type_id` — ідентифікатор типу столика, зовнішній ключ.

### `TableType`

Сутність `TableType` представляє тип столика та його характеристики.

- `id` — унікальний ідентифікатор типу столика, первинний ключ.
- `name` — назва типу столика: `regular`, `window`, `terrace`.
- `description` — опис типу столика.
- `price` — додаткова плата за вибір цього типу столика.

### `Reservation`

Сутність `Reservation` представляє резервування столика користувачем.

Атрибути:

- `id` — унікальний ідентифікатор резервування, первинний ключ.
- `user_id` — ідентифікатор користувача, зовнішній ключ.
- `table_id` — ідентифікатор столика, зовнішній ключ.
- `reservation_datetime` — дата та час резервування.
- `guests` — кількість гостей.

### `Review`

Сутність `Review` представляє відгук користувача про ресторан.

Атрибути:

- `id` — унікальний ідентифікатор відгуку, первинний ключ.
- `user_id` — ідентифікатор користувача, зовнішній ключ.
- `rating` — оцінка ресторану.
- `comment` — текст відгуку.
- `created_at` — дата та час створення відгуку.

## 3. Зв'язки між сутностями

- `User` → `Reservation`: **1:N**. Один користувач може мати декілька резервувань, кожне резервування належить одному користувачу.
- `Table` → `Reservation`: **1:N**. Один столик може мати декілька резервувань у різні дати та час, кожне резервування стосується одного столика.
- `TableType` → `Table`: **1:N**. Один тип столика може бути призначений декільком столикам, кожен столик має один тип.
- `User` → `Review`: **1:N**. Один користувач може залишити декілька відгуків, кожен відгук належить одному користувачу.

## 4. Бізнес-правила

- Один користувач може мати декілька резервувань на різні дати та час.
- Кожне резервування належить одному користувачу та одному столику.
- Один столик може мати декілька резервувань у різні дати та час.
- Один столик не може мати два резервування на однакові дату та час.
- Назва типу столика може мати одне з трьох значень: `regular`, `window` або `terrace`.
- Кожен столик має один тип, який визначається через `table_type_id`.
- Кожен тип столика може мати власну додаткову плату `price` за його вибір.
- Користувач може залишити декілька відгуків.
- Користувач може скасувати власне резервування.
- Після скасування резервування запис про нього видаляється з бази даних.

## 5. Критерії прийняття

- ER-модель містить усі сутності, визначені у специфікації.
- Кожна сутність має первинний ключ.
- Зовнішні ключі визначені для атрибутів, які встановлюють зв'язки між сутностями.
- Зовнішні ключі посилаються на відповідні первинні ключі.
- Кардинальності зв'язків у ER-моделі відповідають описаним зв'язкам між сутностями.
- Назви сутностей та атрибутів в ER-моделі відповідають назвам у специфікації.
- `email` користувача є унікальним.
- `Reservation` містить усі дані, необхідні для опису резервування.
- ER-модель не містить очевидного дублювання одних і тих самих даних.
